## Root cause (resolved)

`counts.total` is defined by spec §2.8 (and the catalog / `DAG_SPEC.md` §5.7) as the number of **registered** tasks. Under early completion (`minSuccessful` / `toleratedFailureCount` / custom `shouldComplete`) the scheduler stops before later tasks start, leaving them **absent** (never recorded). TS always propagated the registered-task count and was correct.

Previously Python, Java, and Go each derived `total` from the size of the _settled/recorded_ task map, which excluded absent tasks. The fix threads the registered-task count through each SDK's result:

- **Python** — `DagResultImpl` now stores an explicit `total_count` (from `len(self._tasks)`), serialized via `totalCount`; `total_count` no longer returns `len(results)`.
- **Java** — `DagExecutor.run` threads `totalTaskCount` (= `tasks.size()`) into `DagExecutionOutcome`; `DagResultImpl.totalCount()` returns the stored value; `SerializedDagResult`/`DagResultSerDes` persist it.
- **Go** — `DagResult` gains a `total` field set to `len(d.tasks)` in `dag_run.go`; `TotalCount()` returns it; `serdes.go` persists/restores it.

In every case only `total` changed — success/failure/skipped counts and the results map are unaffected, and never-started tasks remain absent from the results map (§2.9/§9.6). All four SDKs now match the catalog and each other.

### Secondary note (unchanged, non-blocking, out of scope for this fix)

Java still reports the typed `Dag*Error` being **erased** to a generic `ChildContextFailedException` when a validation error propagates out of `dag()` through the runner (`DagException` constructed with a null `ErrorObject`). The normalized `validation_error` tokens still match the catalog for all five validation scenarios, so this does **not** appear as a record divergence — but it remains a real fidelity gap in the Java error-propagation path, logged for the SDK owners as a follow-up.
