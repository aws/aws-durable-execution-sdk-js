# DAG Public API Review (#5) — Cross-Language Synthesis

> **Scope.** Consolidated API review of the **experimental** public DAG surface across all four SDKs
> (TypeScript/JS, Python, Java, Go), synthesized from the four per-language reviews and checked against
> the canonical specs ([`DAG_SPEC.md`](./DAG_SPEC.md), [`DAG_SPEC_CROSS_LANGUAGE.md`](./DAG_SPEC_CROSS_LANGUAGE.md)).
> **Review only — no SDK code was modified.** The goal is to catch naming / ergonomics / consistency issues
> that are **cheap to change now** (while every symbol is behind an experimental annotation) and expensive to change after stabilization.

**How to read the flags.** Each matrix row is classified as:

- ✅ **Consistent** — same shape, or divergence is pure language idiom (casing, `Optional<>`, free-function-vs-method, functional options). No action.
- 🟨 **Idiomatic divergence** — differs by language but the spec explicitly sanctions it (§3 of the cross-language spec); the observable/wire contract is preserved. Accept-as-idiomatic.
- 🟥 **Accidental inconsistency** — differs in a way **not** explained by idiom; one SDK is an outlier against the other three and/or against its own base SDK. Candidate to fix while experimental.

## 2. Prioritized Recommendations

### 2.A [CHANGE-BEFORE-STABLE]

**Cross-language (highest leverage — a shared contract or an outlier-vs-the-other-three):**

- **C1 — TS `TaskHandle` name access & the `deps()` name collision.** TS exposes `_name` as the customer-facing result key (used by `getResult`/`getStatus`/`DepsMap`) — an underscore field reads as "internal" and is the lone outlier vs Python `.name`, Java `name()`, Go accessor. **Add a clean `readonly name`; hide `_id`/`_resultType`.** Separately, TS names the ordering-only builder `.deps(...)`, colliding with the positional typed data-dep concept; Python (`.after`), Java (`.dependsOn`), Go (`.DependsOn`) all avoid this. **Rename TS `.deps()` → `.after()`** (and settle `after` vs `dependsOn` as the cross-language spelling — recommend `after` for read-flow clarity).
- **C2 — Trailing per-task config param name.** TS names it `options` on all 9 `DagContext` methods; the rest of the JS SDK and Python/Java all use `config`. **Rename TS `options` → `config`.**
- **C3 — Typed result accessor parity (Python).** TS/Java/Go all preserve the dependency result type on the _result_ side (`getResult(handle)→T` / `Result[T]`). Python's `get_result` returns `Any` unconditionally despite `DepsMap` having the `deps[handle]→T` overload and the spec (§2.6) promising it. **Add the `@overload get_result(handle: TaskHandle[T]) -> T`.** Cheap now, hard to retrofit.
- **C4 — Completion-reason type integrity + no premature members.** (a) Go's `type CompletionReason = string` is a bare **alias** — the one break from its own typed-enum pattern (`TriggerRule`/`TaskStatus`/`SkipReason` are defined types). **Make it `type CompletionReason string` (defined).** (b) Java's enum and Go's consts ship `CUSTOM_COMPLETION_SUCCEEDED/FAILED` for a feature that is **deferred to v2** in both languages → dead switch branches / dead consts that can't be removed later without breaking exhaustive switches. **Drop `CUSTOM_COMPLETION_*` from Java & Go until custom completion actually ships** (Python already omits them correctly). Wire values of the shared members stay identical.
- **C5 — TriggerRule `ONE_*` → `ANY_*` (all four) + Java `eval()` leak.** `ONE_SUCCESS`/`ONE_FAILED` evaluate as "at least one" (`.some`), not "exactly one"; `ANY_SUCCESS`/`ANY_FAILED` states the semantics and pairs with `ALL_*`/`NONE_*`. Because the member string is a **shared cross-language wire value**, renaming is cheap while experimental and a breaking wire change after. Also **move Java's public `TriggerRule.eval(List<TaskStatus>)` to an internal evaluator** so the enum stays a pure value type like every other public SDK enum.

**Single-language (important but local):**

- **C6 (Go) — collapse the single shared `Option` type into per-operation option types.** Today `WithTimeout` on a `Step`, `WithCompletion` on a `Callback`, etc. compile and are silently dropped; `WithMaxConcurrency` is overloaded (batch-inner vs DAG-fan-out). At minimum validate/warn on ignored options; ideally split DAG-level vs task-level option types as the base SDK does.
- **C7 (Go) — `WaitForCondition` lost the base op's compile-time safety.** `initialState`/`condition` moved into type-erased `WithInitialState[S]`/`WithCondition[S]`: forgetting `WithCondition` silently completes after one poll; a state-type mismatch silently yields the zero value. **Make initial state a positional param (as the base op does) and validate condition presence at registration.**
- **C8 (Go) — align result naming with the base SDK.** DAG `DagResult.SuccessCount()`/`Err()` sit next to base `BatchResult.SucceededCount()`/`ThrowIfError()` (a DAG Map/Parallel task returns a `BatchResult`, so customers see both spellings in one call site). Pick one policy — recommend pushing base `BatchResult` toward Go-idiomatic `Err()`/`SucceededCount()` cross-cuttingly, or at least document the split. Also settle the op-name abbreviation policy (C-matrix §1.1): either mirror base names (`RunInChildContext`, `WaitForCallback`) or shorten uniformly.
- **C9 (Java) — implement the spec §2.7 positional-arity typed-deps sugar.** `.reads(a)` (declare) and `deps.get(a)` (read) are reconciled only at runtime (`IllegalStateException`). Add 1–3-arity overloads (or a deps-in-signature form) so the common case is compiler-checked; keep `.reads()`+`Deps.get` as the unbounded fallback.

### 2.B [NICE-TO-HAVE]

- **N1 (all) — `started()` / `started_count` parity.** `TaskStatus.STARTED` exists but no `DagResult` exposes a `started`/`started_count` view (base `BatchResult` does in Python). Add for parity so early-completion in-flight tasks are reachable without scanning `results`.
- **N2 (all) — `TaskExecution.startedAt/completedAt` are reserved-but-empty.** Always `Optional.empty()` / `None` / zero today (verified Java; others carry the fields). Consider omitting until a replay-safe timing source lands to avoid a "why always empty" support burden.
- **N3 (Python) — `throw_if_error()` / `DagExecutionError` richness.** It raises with only a formatted string — no `from` chaining, no failed-`TaskExecution` attributes; base `BatchResult` re-raises the original. Attach `.failures: list[TaskExecution]` and chain the cause.
- **N4 (Python) — dead/loose surface.** `DepsArg` is assigned a string literal (dead alias — make it a real `TypeAlias` or delete); `summary_generator` typed `Callable[[Any],str]` should be `Callable[[DagResult],str]`; consider emitting the one-shot `FutureWarning` from `dag_handler` too so nested-only DAGs also warn.
- **N5 (TS) — `DagSummary` exported but SDK-internal.** It's a checkpoint envelope never usefully constructed/consumed by customers; mark `@internal` or drop from the barrel. Likewise `NestedDagConfig` is a pure alias of `DagConfig` — defer exporting until it diverges.
- **N6 (TS) — `DagConfig.completionConfig` shadows the batch field name with an incompatible type.** Either share the shape or give the DAG field a distinct name (e.g. `dagCompletion`).
- **N7 (Java) — `resultType` naming & `Optional<>` record components.** `DagContext` uses `type` where the SDK uses `resultType`; `DagConfig` uses `Optional<>` components while every other config uses nullable fields. Align both (pre-stable renames).
- **N8 (Go) — drop the `Experimental:` comment on unexported `evaluateTrigger`; add a `HasFailure()` convenience** to match base `BatchResult`.
- **N9 (all) — `getResult`/`get_result` `undefined`/`None` ambiguity.** Returns nothing for not-run / failed / skipped **and** for a task that legitimately succeeded with a nullish result. Document that absence ≠ "did not run" and point to `getStatus`.
- **N10 (Python) — entry-point arg order.** `dag(register, name=None, config=None)` inverts the `(name, register)` order of the other three; keeping `name` first (still optional) would improve cross-language muscle memory. Also consider making `deps` keyword-only on registration methods.

### 2.C [ACCEPT-AS-IDIOMATIC]

- **A1 — Typed-deps mechanism per language** (`DepsMap` mapped type / dict+handle overload / `Deps.get(handle)` / `Get[T]`). The spec's "typed-deps spectrum" (§3.2–§3.3): full compile-time safety is only achievable in TS; the other three preserve **result type** via the generic handle and accept runtime key-membership checks. Correct by design.
- **A2 — Entry return shape** (`DurablePromise<DagResult>` / blocking `DagResult` / sync + `dagAsync` twin / `(*DagResult, error)`). Each matches its SDK's concurrency story (§3.1 #16).
- **A3 — Registration surface** (methods vs Go free functions). Go **must** use free `Step[T](d,…)` because methods can't be generic — the only way to mint `TaskHandle[T]` (§3.1 #17). ✅ correct.
- **A4 — Config mechanism** (interface / dataclass / record+builder / functional options) and **error suffix** (Java `…Exception`; Go supersets with `DagValidationError` multi-`Unwrap` + sentinels). Idiomatic; the Go **single-Option-type** part is the accidental exception → C6.
- **A5 — Python 4-member completion enum** (no `CUSTOM_*`) and **Go open string enums with runtime validation** (`DagInvalidTriggerRuleError`). Both spec-sanctioned (§2.A.3, §3.1 #21); string values still match the normative vocabulary.
- **A6 — Java `Optional<T>` on `getResult`** (distinguishes skipped/never-started from a genuine null success) and **sync `register`** everywhere except TS. Justified divergences.
- **A7 — Experimental annotations** — complete and correctly scoped in all four (individually on the four `dag()`/`dagAsync()` methods in Java/TS so the host interface stays GA). Exemplary; no action.
- **A8 — Large-payload strategy split** (TS envelope + design-B reconstruct; Python/Java/Go re-execute the child body). Grounded in real platform behavior (§2.B.6); the customer `summary` string is non-load-bearing in every SDK. Accept.

## 3. Verdict

**The public DAG API is coherent enough to proceed toward stabilization.** The load-bearing, cross-language contract — name-based entity IDs and the `DAG_NODE_T_` delimiter, the trigger-rule truth table, `runIf`, skip semantics, drain-not-fail-fast failure handling, the `COMPLETED_WITH_FAILURES` completion vocabulary, and complete experimental-annotation coverage — is **uniform and conformant to the spec in all four SDKs**. The typed-deps spectrum, entry return shape, and registration surface diverge exactly where the spec sanctions idiomatic divergence. No structural or wire-level defect blocks stabilization.

What remains is a cluster of **cheap, mostly-cosmetic naming/ergonomics fixes** that are far cheaper to make now (behind `@experimental`) than after GA. Most are single-SDK outliers against the other three; a few (TriggerRule vocabulary, completion-reason members) are shared contracts where the change touches all four. None require redesign.

**Top ~5 changes to make first** (ordered by leverage; all cross-language except where noted):

1. **Fix the TS `TaskHandle` outliers** — add clean `readonly name` (retire `_name` as the public key) and rename the ordering-only builder `.deps()` → `.after()` to end the deps/deps collision and match Python/Java/Go.
2. **Rename the TS trailing `options` param → `config`** on all `DagContext` methods (matches the SDK + Python + Java).
3. **Add Python's missing typed `get_result(handle)→T` overload** so result-side typing matches TS/Java/Go and the deps side.
4. **Restore completion-reason type integrity** — make Go `CompletionReason` a _defined_ type (not an alias), and drop the premature `CUSTOM_COMPLETION_*` members from Go **and** Java until custom completion ships.
5. **Rename shared `ONE_SUCCESS`/`ONE_FAILED` → `ANY_SUCCESS`/`ANY_FAILED` across all four** (semantics are "at least one"; it's a shared wire value — free now, breaking later), and move Java's public `TriggerRule.eval()` off the customer enum.

_(Runner-ups, single-SDK but high value: Go's shared `Option`-type footgun and `WaitForCondition` option-ization loss of compile-time safety; Java's spec §2.7 positional-arity typed-deps sugar.)_
